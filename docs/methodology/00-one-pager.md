# 북극성 (One-Pager) — 스펙 게이트 개발(Spec-Gated Development)

> 스펙 게이트 개발(Spec-Gated Development) 방법론의 핵심을 한 장에 담았다. 이 문서는
> **단독으로** 읽혀도 이해되도록 썼다 — 전체 가이드나 헌법 본문을 먼저 읽을 필요는 없다.
> *스택·도메인 중립: 아래에는 특정 프로젝트·언어·프레임워크 이름이 없다.*

---

## ① 한 줄 원칙

> **한 줄 원칙**: 진실(스펙)을 *머릿속이 아니라 문서*에 두고 → 단계를 넘어갈 때마다 그 문서를
> *다시 읽고* → 에이전트가 한 번에 보는 정보는 *작게* 유지한다.

## ② SSoT 코어 — 4개 불변식 (C1~C4)

- **C1 · 진실의 외부화** — 권위 있는 스펙은 저장소 문서에 산다. 코드와 충돌하면 **문서가 이긴다**.
- **C2 · 전환 게이트** — 다음 단계/슬라이스로 넘어가려면 같은 세션 안에서 **상위 진실을 다시
  읽어야** 한다.
- **C3 · 근거 기반 인용** — 규칙을 외워서 인용하지 않는다. **원문 그대로 인용**한다.
- **C4 · 작은 작업 컨텍스트** — 격리(범위 한정 조회·서브에이전트·증분별 작업 공간)로 메인 추론
  스레드를 깨끗하게 유지한다.

## ③ 3-루프 다이어그램

세 개의 루프는 서로 다른 세 프로세스가 아니라 **같은 4개 불변식을 세 시간 규모**(출시 단위 /
증분 단위 / 교훈 단위)로 반복하는 것이다.

```
                ┌──────── SSoT 코어 ────────┐
                │ C1 진실의 외부화            │
                │ C2 전환 게이트              │
                │ C3 근거 기반 인용           │
                │ C4 작은 작업 컨텍스트        │
                └─────────────┬─────────────┘
          ┌───────────────────┼───────────────────┐
     [ 기획 루프 ]        [ 구현 루프 ]        [ 학습 루프 ]
   요구→전략→전술→데이터   게이트→스펙→계획      캡처→메모리/KB
   (단계마다 상위 재독)    →격리→red/green      →사례연구→플레이북
                         →리뷰→검증→통합        갱신→SSoT 피드백
          └───────────────────┴───────────────────┘
                    (같은 4불변식, 세 시간 규모)
```

구현 루프(Build)는 **8단계**로 실행된다 — **게이트 → 스펙 → 계획 → 격리 → TDD → 리뷰 → 검증 →
통합**. 아래 체크리스트 2개는 그중 처음(게이트)과 끝에서 두 번째(검증)를 즉시 실행 가능한
형태로 편 것이다.

## ④ 즉시 실행 체크리스트

**A. 슬라이스 착수 게이트** — 슬라이스를 시작하기 전, 같은 세션 안에서:
- [ ] 이 슬라이스가 걸리는 요구사항/수용 기준을 스펙 문서에서 **다시 읽었다** (기억으로 인용하지
  않았다)
- [ ] 이 슬라이스가 건드리는 **경계**(모듈/레이어/영역)를 확인했다
- [ ] 무엇을 읽고 무엇을 확인했는지 **"참조 문서" 노트**를 남겼다

**B. 완료(검증) 게이트** — "완료"라고 말하기 전, 커밋하기 전:
- [ ] 실제 명령을 **실행**했다 (테스트/빌드/린트/수동 확인 등)
- [ ] 그 **출력을 읽고** 확인했다
- [ ] **증거 없이는 "완료" 없음** — 명령과 출력 없이 완료를 선언하지 않았다

---

*이 두 체크리스트는 헌법(`CONSTITUTION.md`)의 비협상 항목 중 **게이트 순서**와
**검증-전-완료**를 슬라이스 단위에서 바로 실행 가능한 형태로 편 것이다. 전체 맥락과 기획
루프·학습 루프는 `01-guide.md`를 참고.*
