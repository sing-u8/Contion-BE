# 방법론 매뉴얼 (Guide) — 스펙 게이트 개발(Spec-Gated Development)

> 이 문서는 번들의 **본 매뉴얼**이다. 단일 진실인 `CONSTITUTION.md`를 **풀어서 설명**하고
> (같은 어휘를 그대로 재사용한다), 합성 아키텍처는 `02-composition.md`를 **요약·링크**한다.
> 무엇이든 이 매뉴얼과 `CONSTITUTION.md`가 어긋나면 **`CONSTITUTION.md`가 이긴다**(C1 · 진실의
> 외부화). 한 장 개요만 필요하면 `00-one-pager.md`를 보라.
>
> *본문(0~8절)은 완전히 스택·도메인 중립이다 — 특정 프로젝트·언어·프레임워크 이름이 없다.
> 실제 프로젝트의 고유명이 중립 표현으로 어떻게 번역되는지는 맨 끝 **부록**에 예시로만 실린다.*

## 0. 핵심 원칙 & 이식성 — 왜 모델·스킬팩을 갈아끼워도 살아남는가

> **한 줄 원칙**: 진실(스펙)을 *머릿속이 아니라 문서*에 두고 → 단계를 넘어갈 때마다 그 문서를
> *다시 읽고* → 에이전트가 한 번에 보는 정보는 *작게* 유지한다.

이 방법론은 하나의 **뼈대(spine)** 로 이뤄진다: **SSoT 코어(4개 불변식 C1~C4)** 와 그것을 세 시간
규모로 반복하는 **세 개의 루프**다. 세 루프는 서로 다른 세 프로세스가 아니라 **같은 4개 불변식을
세 시간 규모(출시 단위 / 증분 단위 / 교훈 단위)로 반복**하는 것이다.

```
                ┌──────── SSoT 코어 ────────┐
                │ C1 진실의 외부화            │
                │ C2 전환 게이트              │
                │ C3 근거 기반 인용           │
                │ C4 작은 작업 컨텍스트        │
                └─────────────┬─────────────┘
          ┌───────────────────┼───────────────────┐
     [ 기획 루프 ]        [ 구현 루프 ]        [ 학습 루프 ]
   요구→전략→전술→데이터   게이트→스펙→계획      캡처→메모리/KB
   (단계마다 상위 재독)    →격리→red/green      →사례연구→플레이북
                         →리뷰→검증→통합        갱신→SSoT 피드백
          └───────────────────┴───────────────────┘
                    (같은 4불변식, 세 시간 규모)
```

**왜 모델·스킬팩 이식성이 생기는가.** 규율이 **특정 모델의 기억이 아니라 저장소(문서·게이트·
플레이북·훅) 안에** 살기 때문이다. 모델의 컨텍스트 창은 세션마다 리셋되고 기억은 휘발한다. 하지만
진실이 저장소 문서에 외부화되어 있고(C1), 전환마다 그 문서를 다시 읽게 강제되고(C2), 규칙은 외우지
않고 원문 인용되고(C3), 한 번에 보는 정보가 작게 유지되면(C4) — **어떤 모델이 오든, 어떤 스킬 팩을
얹든** 같은 기준을 본다. 즉 이식성과 불변성은 같은 뿌리에서 나온다: *진실을 사람·모델의 머릿속에서
빼내 저장소에 두는 것.*

- **모델 이식성** — 모델을 교체해도 저장소의 스펙·게이트·훅은 그대로다. 새 모델은 첫 세션부터
  같은 문서를 읽고 같은 게이트를 밟는다.
- **스킬팩 이식성** — 스킬 팩은 각 단계의 "어떻게"만 제공하는 **기법 제공자**일 뿐이다(8절). 팩을
  켜고 끄고 바꿔도 "언제·무엇"을 정하는 뼈대는 팩 바깥(Tier 0)에 있으므로 흔들리지 않는다(전체
  Tier 0/1/2 모델은 8절 및 `02-composition.md` 참조).

이 매뉴얼의 나머지는 이 뼈대를 펼친다: **1절**은 SSoT 코어의 4개 불변식을, **2~4절**은 세 루프를,
**5절**은 기능 하나를 세 루프로 통과시키는 워크쓰루를, **6~8절**은 도입·이식·합성을 다룬다.

## 1. SSoT 코어 — 4개 불변식(C1~C4)

모든 zoom 레벨에서 성립하는 **비협상 불변식** 4개다. 각 불변식을 **원칙 · 이유 · 중립 메커니즘 ·
스멜 테스트** 네 각도로 설명한다. (정식 정의는 `CONSTITUTION.md` §②.)

### C1 · 진실의 외부화 (Externalized truth)

- **원칙** — 권위 있는 스펙은 버전 관리되는 저장소 문서에 산다. 코드와 충돌하면 **문서가 이긴다**.
  상위 계층이 하위 계층을 제약한다.
- **이유** — 모델의 컨텍스트는 세션마다 리셋되고, 사람의 기억도 드리프트한다. 진실이 문서에 있으면
  누가·어느 세션에 오든 같은 기준을 본다. 이것이 모델·스킬팩을 갈아끼워도 살아남는 뿌리다.
- **중립 메커니즘** — 계층형 SSoT 문서 세트(요구사항 → 전략 → 전술 → 데이터) + **용어집** +
  **경계/혼동 카탈로그**를 저장소에 둔다. 규칙 파일에 "문서 > 코드"를 명문화한다.
- **스멜 테스트** — "이 규칙, 어디에 적혀 있죠?"에 *문서 경로+위치*로 답하지 못하면 진실이
  외부화되지 않은 것이다. 코드가 스펙과 다른데 코드를 진실로 삼고 있으면 위반이다.

### C2 · 전환 게이트 (Transition gates)

- **원칙** — 다음 단계/다음 슬라이스로 넘어가려면 **같은 세션 안에서 상위 진실을 다시 읽어야**
  한다. 게이트는 싸고, 강제적이고, 반복된다.
- **이유** — 기억에 기대어 진행하면 매 전환마다 조금씩 드리프트한다. 재독은 값싸고(몇 분) 그
  드리프트를 전환마다 0으로 리셋한다. 싸기 때문에 자주 반복할 수 있다.
- **중립 메커니즘** — **착수 게이트 체크리스트**(재독 · 경계 확인 · "참조 문서" 노트)와 **단계
  게이트**(하위 단계 편집 전 상위 단계 재독). 기계적 훅이 커밋 시 "게이트 노트" 존재를 확인한다.
- **스멜 테스트** — 슬라이스를 시작하는데 *방금 무엇을 읽었는지* "참조 문서" 노트가 없다면 게이트를
  건너뛴 것이다. 요구사항을 "기억으로" 인용하고 있으면 위반이다.

### C3 · 근거 기반 인용 (Grounded citation)

- **원칙** — 규칙을 외워서 인용하지 않는다. **원문 그대로 인용**한다. 헷갈리기 쉬운 규칙 쌍은 별도
  **경계 카탈로그**에 기록한다.
- **이유** — 외운 규칙은 조용히 변형된다 — 특히 숫자·식별자·경계에서. 원문 인용은 그 변형을 막고,
  인용을 *검증 가능*하게 만든다(출처를 따라가 대조할 수 있다).
- **중립 메커니즘** — 인용할 때 **원문 발췌 + 출처(문서·버전·위치)** 를 함께 붙인다. 혼동되는 규칙
  쌍은 경계 카탈로그에 "이건 이거고 저건 저거다"로 못 박는다. 조회는 범위를 좁혀서 한다(C4).
- **스멜 테스트** — 인용에 출처가 없다면 근거가 없는 것이다. 비슷한 두 규칙을 뭉뚱그려 말하고
  있다면 경계 카탈로그가 비어 있다는 신호다.

### C4 · 작은 작업 컨텍스트 (Small working context)

- **원칙** — 격리(범위 한정 조회, 서브에이전트, 증분별 작업 공간)로 메인 추론 스레드를 깨끗하게
  유지한다.
- **이유** — 컨텍스트가 넘치면 모델이 초점을 잃고 인용이 흐려진다(C3가 함께 무너진다). 작은
  컨텍스트가 정확도를 지키고, 격리가 증분 간 충돌을 차단한다.
- **중립 메커니즘** — 큰 스펙은 통째로 밀어 넣지 말고 **범위 한정 조회**(검색 / 서브에이전트)로 필요
  발췌만 가져온다. 슬라이스마다 **격리 작업 공간**(작업 트리/브랜치)을 쓴다. **한 번에 한 슬라이스.**
- **스멜 테스트** — 메인 스레드에 관련 없는 파일 수십 개가 열려 있다면 컨텍스트가 오염된 것이다. 한
  세션에서 여러 슬라이스를 동시에 굴리고 있으면 위반이다.

> 이 넷은 **비협상**이다. 어떤 스킬 팩·도구도 이것들을 바꿀 수 없다(8절 · `CONSTITUTION.md` §⑧).
> 이는 `CONSTITUTION.md` §⑧의 **4개 비협상 항목**(게이트 순서 · SSoT 우선 · 근거 인용 ·
> 검증-전-완료)과 이어지며, 그중 **게이트 순서**와 **검증-전-완료**는 특히 기계적 훅으로도
> 강제된다.

## 2. 기획 루프(Plan) — 단계 · 게이트 · 소규모 축약

**기획 루프(Plan)** 는 하향식 진실 구축이다: 요구사항 → 전략 설계 → 전술 설계 → 데이터 설계. 각
단계의 산출이 다음 단계를 **제약**하고, 각 단계는 **상위 단계 재독을 게이트로** 삼는다. 산출물은
계층형 SSoT + 용어집 + 경계 카탈로그다.

| 단계 | 질문 | 산출 |
| --- | --- | --- |
| **P1 요구사항** | 시스템이 **무엇**을 해야 하나 | 요구사항 ID + 수용 기준 |
| **P2 전략 설계** | 어떻게 **바운디드 영역 + 공용 언어**로 가르나 | 컨텍스트 맵 · 용어집 |
| **P3 전술 설계** | 각 영역의 **빌딩블록·규칙·이벤트·식별자** | 도메인 모델 |
| **P4 데이터 설계** | **상태를 어떻게 저장·조회**하나 | 스키마 · 쿼리 형태 |

**단계 게이트.** 하위 단계 문서를 편집하기 전에, 같은 세션에서 상위 단계 문서를 다시 읽는다(C2).
예: 데이터 설계(P4)를 손대기 전 요구사항(P1)·전략(P2)·전술(P3)을 재독한다. 이렇게 하면 하위 결정이
상위 진실에서 이탈하지 않는다.

**소규모 프로젝트 축약법.** 작은 프로젝트는 네 단계를 물리적으로 나눌 필요가 없다 — **단계 수는
줄여도 되지만 순서와 게이팅은 불변**이다. 예컨대 한 문서 안에 "무엇(P1) → 어떻게 가르나(P2/P3) →
어떻게 저장(P4)" 순서로 섹션만 두어도 된다. 핵심은 *상위를 정한 뒤 하위로 내려가고, 하위를 고치기
전 상위를 다시 본다*는 방향과 게이트를 지키는 것이다. (도입은 처음부터 4단계를 다 세우지 않는다 —
6절 참고.)

## 3. 구현 루프(Build) — 슬라이스 8단계 라이프사이클

**구현 루프(Build)** 는 슬라이스(작게 자른 증분) 단위 실행이다. 순서는 고정이다:

> **게이트 → 스펙 → 계획 → 격리 → TDD → 리뷰 → 검증 → 통합**

1. **게이트(재독)** — 이 슬라이스가 걸리는 요구사항/수용 기준을 재독하고, 건드리는 **경계**를
   확인하고, "참조 문서" 노트를 남긴다(C2·C3). 기억으로 인용하지 않는다.
2. **스펙** — 슬라이스를 작은 설계로 브레인스토밍한다(무엇을 · 어떤 경계 안에서 · 어떤 수용 기준).
3. **계획** — 단계별 구현 계획을 세운다(무엇을 먼저, 무엇을 다음 슬라이스로 미룰지).
4. **격리** — 증분별 **격리 작업 공간**(작업 트리/브랜치)으로 다른 작업과의 충돌을 차단한다(C4).
5. **TDD(red/green)** — **실패 테스트 먼저(red)** → 통과시키는 구현(green) → 리팩터. 수용 기준을
   테스트로 못 박는다.
6. **리뷰** — 튜닝된 리뷰어(플레이북/에이전트/사람)가 컨벤션 + **인용된 진실** 대비로 점검한다.
7. **검증** — 실제 명령을 돌리고 **출력을 읽는다**. **증거 없이는 "완료" 없음.**
8. **통합** — 브랜치 플로우로 통합(머지)한다. **보호 브랜치 직접 커밋 금지**(기계적 훅이 강제).

**모든 증분이 인용된 스펙에 다시 접지(re-ground)된다** — 1단계 게이트가 매 슬라이스마다 상위 진실을
재독하게 만들기 때문이다. 8단계는 세 층으로 요약된다: *들어가기 전 접지(1~4) → 만들기(5) → 내보내기
전 방어(6~8).* 각 단계의 "어떻게"는 스킬 팩이 채울 수 있다(8절) — 하지만 **순서와 존재 자체는
뼈대가 소유**한다.

## 4. 학습 루프(Learn) — 캡처 표면 + 피드백 엣지

**학습 루프(Learn)** 는 진실 유지보수다. 비자명한 결과를 **캡처**하고, 그것을 규칙/플레이북으로
**승격**하고, 수정 사항을 **SSoT로 피드백**해 루프를 폐합한다.

- **지속 메모리** — 세션을 넘어 사는 사실/결정/피드백 저장소. 에이전트가 **매 세션 참조**한다.
- **아키텍처 KB** — 시스템이 실제로 어떻게 동작하는지 살아있는 설명서.
- **사례 연구** — 슬라이스별 회고: **무엇이 깨졌나 · 왜 · 어떻게 고쳤나 · 교훈**.
- **플레이북 갱신** — 반복되는 리뷰 지적을 규칙/리뷰어로 **승격** → 다음 슬라이스가 미리 회피한다.
- **피드백 엣지** — 교훈이 **SSoT(C1)** 와 게이트/플레이북을 갱신한다 → 루프가 닫힌다.

핵심은 **피드백 엣지**다. 학습이 메모에서 끝나면 다음 슬라이스가 같은 실수를 반복한다. 교훈이
경계 카탈로그·요구사항·플레이북 같은 **외부화된 진실**로 흘러 들어가야(C1), 이후 슬라이스의
게이트(C2)에서 자동으로 다시 읽힌다. 즉 학습 루프의 출력은 기획 루프·구현 루프의 **입력**이 된다.

## 5. 워크쓰루 — 기능 하나를 아이디어에서 출시까지

세 루프가 하나의 기능에서 어떻게 맞물리는지 **도메인 중립 예시**로 통과시킨다.

> **기능 아이디어**: 사용자가 목록의 **항목을 "북마크"** 하고, **"북마크한 항목만"** 보기로 걸러
> 볼 수 있다. 북마크는 사용자별로 사적이다.

### Pass 1 — 기획 루프(Plan): 진실을 세운다

새 기능이 도메인 개념(북마크)을 들여오므로 먼저 기획 루프를 한 바퀴 돈다.

- **P1 요구사항** — *무엇?* 사용자는 항목을 북마크/해제할 수 있고, "북마크만" 필터로 목록을 좁힌다.
  수용 기준 예: `REQ-1` 이미 북마크한 항목을 다시 북마크해도 **중복이 생기지 않는다(멱등)**;
  `REQ-2` 한 사용자의 북마크는 다른 사용자에게 보이지 않는다(사적). **산출**: 요구사항 ID + 수용
  기준. (최상위 단계라 재독 게이트 없음.)
- **P2 전략 설계** — *어떻게 가르나?* 두 **바운디드 영역**으로 나눈다: 항목이 사는 **카탈로그
  영역**과 사용자의 활동이 사는 **활동 영역**. 북마크는 활동 영역의 개념이다. **공용 언어**: "저장 /
  즐겨찾기 / 담기"처럼 흩어진 유사어를 **"북마크" 하나로 확정**해 용어집에 적는다. **게이트**: P1 재독.
- **P3 전술 설계** — *빌딩블록·규칙·이벤트·식별자.* 규칙: **한 사용자가 한 항목을 최대 한 번**
  북마크한다(멱등 불변식, `REQ-1`의 도메인 표현). 식별자: `(사용자ID, 항목ID)` 복합키. 이벤트:
  "항목이 북마크됨". **혼동 경계**: "북마크 **해제**"와 "항목 **삭제**"는 다른 연산이다(해제는 링크만
  끊고 항목은 남는다) → **경계 카탈로그**에 헷갈림 쌍으로 못 박는다(C3). **게이트**: P1·P2 재독.
- **P4 데이터 설계** — *어떻게 저장·조회하나.* 저장: `(사용자ID, 항목ID)` **유니크 제약**을 가진
  링크 테이블 — 멱등을 데이터 계층에서까지 보장한다. 조회: "북마크만" 뷰 = 링크 테이블 조인 + 현재
  사용자 필터. **게이트**: P1·P2·P3 재독.

**기획 루프 산출**: 계층형 SSoT(작으면 한 문서에 4섹션) + 용어집("북마크") + 경계 카탈로그("해제 ≠
삭제").

### Pass 2 — 구현 루프(Build): 슬라이스 하나를 8단계로 통과

첫 슬라이스를 **"북마크 추가(멱등 처리 포함)"** 로 얇게 자른다(필터 뷰는 다음 슬라이스).

1. **게이트** — `REQ-1`(멱등)·`REQ-2`(사적) 재독, 경계(활동 영역·링크 테이블) 확인, "참조 문서"
   노트 작성.
2. **스펙** — 이 슬라이스 = "북마크 추가 연산 + 중복 요청 멱등 처리". 작은 설계로 브레인스토밍.
3. **계획** — 링크 테이블 준비 → 도메인 연산(추가) → 진입점 배선. 필터 뷰는 **다음 슬라이스로 미룸**.
4. **격리** — 이 슬라이스용 격리 작업 공간(작업 트리/브랜치)에서 작업.
5. **TDD(red/green)** — 실패 테스트 먼저: *"같은 항목을 두 번 북마크해도 링크가 하나"*(멱등) →
   red → 구현 → green → 리팩터. `REQ-2`(사적)도 테스트로 고정.
6. **리뷰** — 튜닝된 리뷰어가 컨벤션 + 인용된 수용 기준 대비 점검. 특히 "해제와 삭제를 섞지
   않았는가"(P3 경계)를 확인.
7. **검증** — 테스트·빌드 명령을 **실제로 돌리고 출력을 읽는다**. 증거 없이 "완료" 없음.
8. **통합** — 브랜치 플로우로 통합. 보호 브랜치 직접 커밋 금지(훅이 차단).

### Pass 3 — 학습 루프(Learn): 교훈을 진실로 되돌린다

- **캡처** — 비자명한 결과: *동시에 두 번 북마크 요청이 오면 유니크 제약이 중복 삽입을 막지만, 코드가
  그 제약 위반 에러를 **삼켜서** 겉으로 멱등처럼 보이게 해야 한다*는 교훈 → **지속 메모리**에 기록.
- **사례 연구** — 이 슬라이스 회고: *무엇이 깨졌나*(동시 요청 시 에러가 사용자에게 노출됨) · *왜* ·
  *어떻게 고쳤나* · *교훈*.
- **플레이북 승격** — 리뷰에서 반복된 "해제 ≠ 삭제" 지적을 **리뷰 플레이북 규칙**으로 승격 → 다음
  슬라이스가 미리 회피.
- **피드백 엣지** — 멱등·동시성 경계가 더 명확해졌으니 **경계 카탈로그(C1 SSoT)** 를 갱신한다 →
  다음 슬라이스의 게이트(C2)에서 자동으로 다시 읽힌다. **루프 폐합.**

이 한 바퀴가 방법론 전체의 축소판이다: *진실을 세우고(Plan) → 그 진실에 접지해 만들고(Build) →
배운 것을 진실로 되돌린다(Learn).* 두 번째 기능부터는 보통 기획 루프를 가볍게(또는 축약) 돌고 곧장
구현 루프로 들어간다.

## 6. 점진 도입 — day-1 최소에서 시작해 아플 때 늘린다

전부를 한 번에 세우지 않는다. **가장 싸고 ROI 높은 습관부터** 시작하고, 아플 때 계층을 늘린다(YAGNI).

1. **day-1 최소** — 얇은 **외부화 스펙**(한 문단이라도) + **착수 게이트(재독)** + **검증-전-완료**.
   이 셋만으로도 드리프트와 "증거 없는 완료"가 즉시 줄어든다.
2. **SSoT 코어를 키운다** — 스펙을 계층으로 나누고, **경계/혼동 카탈로그**와 **인용 규율(C3)** 을
   더한다.
3. **완전한 단계형 기획 루프** — 요구사항 → 전략 → 전술 → 데이터 4단계와 단계 게이트를 세운다
   (2절). 소규모는 축약해도 순서·게이팅은 유지.
4. **학습 루프 인프라** — 지속 메모리 · 아키텍처 KB · 사례 연구 · 플레이북 승격(4절). 그리고 스킬 팩
   합성(8절)과 **기계적 훅**을 붙인다.

**원리**: 게이트 + 검증처럼 가장 값싼 습관이 가장 큰 드리프트를 막는다 — 그걸 먼저 넣고, 도메인이
커져 실제로 아플 때 계층을 늘린다. (성숙하고 도메인이 큰 프로젝트는 반대로 무거운 기획을 선적재할
수도 있다 — 그건 이미 복잡도가 크기 때문이다. 신규·소규모라면 위 순서를 권한다.)

## 7. 아무 AI 에이전트에서 굴리기 — 포인터 배선과 부재 도구 에뮬레이션

뼈대의 규율은 특정 도구 기능이 아니라 **저장소**에 산다(0절). 따라서 어떤 에이전트에서도 굴릴 수
있다. 방식은 두 가지: **헌법 포인터 배선**과 **부재 기능 에뮬레이션**이다.

**헌법 포인터 배선.** 단일 진실은 중립 `CONSTITUTION.md` 하나이고, 각 도구가 세션 시작 시 자동 로드
하는 **진입 파일**은 본문을 복제하지 않고 그것을 **가리키기만** 한다.

- 도구별 진입 파일(예: `CLAUDE.md` · `AGENTS.md` · `GEMINI.md` 등, 도구마다 파일명이 다름)은 각각
  *"세션 시작 시 `CONSTITUTION.md`를 읽고 그대로 따르라"* 를 지시한다. 새 에이전트가 생기면 **포인터
  한 장만** 추가하면 된다(본문은 그대로 하나).
- **하드코어 인라인 미러(권장 기본)** — 진입 파일은 자동 로드되지만 본문은 포인터를 따라가야 열리
  므로, **4개 비협상 항목**만 짧게 진입 파일에 인라인으로 복사해 *항상 컨텍스트에* 둔다(방어 다중화).
  전체 방법론은 본문에만 둔다. (자세한 계층/조항은 `02-composition.md`.)

**부재 기능 에뮬레이션.** 서브에이전트·지속 메모리·스킬/게이트가 없는 도구에서도 불변식은 근사할 수
있다.

- **서브에이전트가 없다 → C4를 수동으로.** 범위 한정 검색으로 필요 발췌만 가져오고, 큰 조회는 별도
  대화/창으로 빼서 메인 스레드를 오염시키지 않는다.
- **지속 메모리가 없다 → 저장소 안 메모리 파일로.** 세션을 넘는 노트를 저장소의 한 문서에 두고, 매
  세션 첫머리에 **수동으로 로드**한다(도구가 자동 로드 못 해도 사람이 붙여넣는다).
- **스킬/게이트 개념이 없다 → 체크리스트로.** 착수 게이트·완료 게이트를 체크리스트로 만들어 손으로
  밟는다(`00-one-pager.md`의 즉시 실행 체크리스트 2개가 그대로 쓰인다).
- **규칙 파일을 아예 읽지 않는 도구 → 기계적 훅이 유일한 백스톱.** 진입 파일을 자동 로드하지 않는
  도구는 프롬프트 권위가 없다. 이때는 **git pre-commit / CI 훅**이 유일한 방어선이다 — 도구가 프롬
  프트를 읽든 안 읽든 **커밋 시점에** 보호 브랜치·게이트 노트·검증 마커를 강제한다. 그래서 훅 템플릿
  을 번들의 필수 산출물로 둔다(이 엣지 케이스의 정식 논의는 `02-composition.md`).

## 8. 스킬 팩과의 합성 — 뼈대가 안 바뀌는 이유

이 뼈대 위에 슬래시 커맨드·스킬 팩을 얹어도 **뼈대는 달라지지 않는다.** 그 이유의 캐노니컬 문서는
**`02-composition.md`** 이며, 여기서는 요점만 요약한다(표는 중복하지 않고 링크한다).

- **3-Tier 우선순위.** **Tier 0(헌법)** = 뼈대 + 우선순위·합성 조항, 최상위·불변. **Tier 1(운영
  스킬)** = 게이트를 실제로 걷게 하는 얇은 스킬, Tier 0 종속. **Tier 2(기법 팩)** = 각 단계의
  "어떻게"만 제공, 종속(충돌 시 Tier 0 승). **횡단(기계적 훅)** = 스킬 선택과 무관하게 하드 불변식을
  강제.
- **한 단계는 한 팩 스킬만 드라이브한다.** 뼈대가 "언제·무엇"을, 팩이 "어떻게"를 맡는다. 두 팩을 같은
  단계에 **동시에** 걸지 않는다 — 하나를 드라이버로 고르고 나머지는 참고만 한다.
- **4개 비협상 항목이 팩 기본동작을 누른다.** 팩의 기본동작(자동 커밋 · 게이트 스킵 · 리뷰 우회 ·
  근거 없는 인용 등)이 **게이트 순서 · SSoT 우선 · 근거 인용 · 검증-전-완료** 와 충돌하면 **헌법이
  이기고 그 동작은 무효**다. 프롬프트 선언으로 부족하면 기계적 훅으로 하드 차단한다.
- **팩 무관성(Level A / Level B).** 4개 비협상 항목(Level A)은 *어떤* 팩·도구·에이전트에도 성립한다
  — 메커니즘이 팩을 열거하지 않기 때문이다. 팩별 단계 매핑(Level B)은 **예시**이자 편의다: 새 팩이
  오면 매핑 표에 **행 하나** 추가하면 되고, 추가 전에도 Level A는 이미 보장된다.

**예시로서의 합성 매핑.** `02-composition.md` §③은 실재하는 두 스킬 팩 — **superpowers** 와
**gstack** — 이 뼈대의 Build 8단계를 각각 어떻게 채우는지 **예시**로 보여준다. 그 표가 통째로 없어도,
또는 표에 없는 제3의 팩을 쓰더라도 뼈대의 불변성(Level A)은 그대로다. **새 팩 온보딩**은 세 단계다:
① 팩 스킬을 8단계에 매핑 → ② 팩 기본동작이 4개 비협상 항목과 충돌하는지 점검 → ③ 충돌하면 헌법이
이기고 필요 시 훅으로 하드 차단. (전체 매핑 표·조항 원문·엣지 케이스는 **`02-composition.md`** 참고.)

쓴 것도 같은 이유다 — 뼈대는 도메인을 갈아끼워도 그대로 성립한다.
